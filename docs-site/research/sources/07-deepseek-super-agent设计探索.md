## 核心论点

单会话 agent 的瓶颈:**单任务上限取决于模型能力,多任务上限取决于人的注意力**(人通常只能同时跟进 3–5 个活跃会话)。出路是把 agent 从"人手动驱动的单个会话"解耦出来,成为跨会话保持上下文、并行处理多个复杂任务的持续实体(Super-agent)。

四个特征:**Continuous**(跨渠道像同一个 agent)、**Productive**(多任务并行,不阻塞)、**Proactive**(监听环境事件,值得处理才行动,否则安静)、**Persistent**(常在线,自动从异常恢复)。作者认为单个 ReAct 循环给不了这四点,必须由外围系统架构提供。

## 五个模块

| 模块 | 要点 |
| --- | --- |
| 两级架构 | **Router**(长存会话,只和人交互并派活,可以没有 Bash 工具,用较轻模型即可)+ **Worker**(上下文隔离,一个任务一个,用最强模型,不直接与人对话,只向 Router 汇报)。Router 不拆解任务,区别于 Agent Team |
| 事件驱动 | 环境事件(Trigger)是主要输入。**Fast Path/Slow Path**:先用确定性代码(来源、群、白名单)过滤噪声,再让模型判断语义。**订阅与直通**:同一 Thread 的后续事件由代码直接送到已订阅的 Worker,不经 Router |
| 上下文组织 | 把上下文窗口当缓存:**Inline & Spill**(近处信息内联,超限的留引用)+ **Chain of Recall**(对象 ID 形成引用图,逐跳召回) |
| 提前行动 | 借"推测执行":后台先复现并尝试修复,确认有价值才发言,否则全程安静 |
| 全双工多渠道 | 用异步 `start()`/`stop()` 替代阻塞调用;IM 渠道克制(文中验证的硬规则:**每条回复 ≤100 字**),GitHub/邮件则输出结构化高密度内容 |
| 计算/状态/环境分离 | 无状态云容器 + 数据库存会话;**执行环境留在原处**,端点只装轻量 daemon(BYOM,自带机器)。理由:真实环境含未提交改动、私有凭证、内网依赖,难以同步 |
| Watchdog | 主系统之外的独立控制循环,不仅看进程存活,还用模型判断 Worker 是否**有实质进展或已偏离目标** |

## 实验(作者自述为初步、合成负载,仅供参考)

- 消融:约 300 条消息、约 20 个工作请求,每种设计跑 5 次。Super-agent 任务完成 p50 12.4 分钟 / p95 15.7 分钟;单会话 + 子 agent 在中性提示下**5 次都没有调用子 agent**,p95 达 29.5 分钟。关闭"直通"后完成时间相近,但 Router 决策多约 30%,缓存读 token 从 23.2M 增到 31.8M(约 +37%)。
- Router 批处理:触发频率从约 1 升到约 40 次/分钟,平均批大小 1.0→2.8,单次决策摊销推理时间 6.4s→1.6s。结论:当前团队规模下单个 Router 够用,无需过早分片。
- 编码任务在实验里由"只消耗时间的工具"模拟,所以测的是调度,不是执行质量。

## 作者自己列出的开放问题

两级架构怎样扩展;没有会话时怎样与 agent 协作(任务呈现与项目管理);上下文边界与 A2A;**安全与隐私**——事件驱动让更多不可信输入进入 agent,云端 Agent Loop 一旦被入侵或提示注入,所有连接的端点设备都可能被接管;凭证只要能进入模型上下文就可能泄露,需要"使用凭证而不看见凭证"的机制。长期记忆在运行数月后会成为主要瓶颈。

## 值得记住的措辞

- 会话应该是系统的实现细节,不是用户的心智负担。
- 把 agent 做成"在人们已有工作环境里常在线的协作者",而不是等待指令的聊天窗口。
