## 核心主张

agent 反复失败时,不要改形容词或换模型,而要检查模型周围的环境(harness)。提示工程改进指令,上下文工程决定模型看到什么,harness 工程建造模型行动所处的世界。

## Harness 的七项职责

1. 把请求变成**契约**(目标、输入、输出、约束、`done_when`),防止任务被悄悄重新定义。
2. 给 agent 一张**地图**(根部小型指引,指向各处详细资料),而不是巨型手册。
3. 在正确环境里暴露**工具**:每个工具要有明确目的、可预期输出、显式失败状态、权限边界。
4. 把记忆**外置为持久状态**:对话不是系统记录;决策、产物、失败、未决风险存在上下文之外。
5. **先加传感器再加自主性**:测试、lint、截图、日志、schema 校验把"质量"变成证据。
6. **权限在模型之外执行**:模型建议 → 策略检查 → 工具执行;不要让同一个概率系统既制定计划、又批准风险、又执行副作用。
7. 记录**轨迹**并本地恢复。

## 可抄的具体做法

- **规则写两遍**:一遍是 agent 能读懂的指引(解释为什么),一遍是它绕不过的机械检查(如 lint 禁止 UI 层直接 import 仓库层)。
- 每个循环都要有**重试上限和预算**,失败后升级到人工审阅。
- 不同产物对应不同的验证方式:代码→测试/类型/lint;UI→渲染+截图;**研究→来源核对+矛盾核对**;数据→schema+范围+新鲜度。
- 成熟度 Level 0–3:提示+模型 → 指引+工具 → 结构化状态+测试+有界循环 → 权限+轨迹+恢复+人工门禁。
- 失败→对策对照表(缺上下文加地图、重复循环加重试上限、不安全动作加权限门、丢失决策存持久状态等)。
- 12 项检查清单,包含"成功是否在执行前定义"、"风险转移是否有证据"、"是否可回滚"。
- 文中的运行轨迹示例字段:上下文来源、策略版本、模型路由、用到的工具、测试结果、人工纠正次数、重试次数、成本、被接受的产物、回滚点。
