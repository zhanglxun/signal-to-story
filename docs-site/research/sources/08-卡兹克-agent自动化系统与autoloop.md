## 作者的出发点

直接引用并回应 DeepSeek 文章"多任务上限取决于人的注意力"。方法:**把任务发起点从人身上拿掉,由信号(事件)触发 agent**;人只做最后的决策(他称为"批奏折")。

## 系统结构(第一篇)

1. **事件中台**:所有事件(Webhook、定时、飞书消息、告警)先到一个小服务。统一事件格式:**来源、类型、对象、一句话摘要、回链**。
2. **`rules.json` 路由**:每条规则写明 `when`(来源/类型)、`to`(哪个 agent)、`cwd`、`skill`、`ask`、`group`(同组同时只跑一轮)、`parallel`(并行度)、`tell`(`needed` 表示只在必须决策时才通知人)。换 agent 或模型只改一行。
3. **去重**:同一件事被重复发送是常态,中台统一去重,避免多个 agent 同时改同一处。
4. **长轮询接单**:本地 Mac 在内网,中台推不进去,所以 Mac 上的接单程序挂在中台上最长等 50 秒,有活即接,没活再挂。Mac 不暴露公网。
5. **单一出口**:无论哪个 agent 找人,只走飞书里的助理一个通道,避免刷屏。
6. **数据沉淀**:每件事记录来源、交给谁、结论、是否需要人、后续,并可跳转到当时的 agent 会话。
7. **Skill = SOP**:每个自动化任务配一个专属 skill;改任务行为就改 skill,不改执行逻辑。
8. **本地运行的理由**:仓库、发布权限、飞书身份、登录好的浏览器都在自己的两台 Mac 上;放云上要在每家复制一份登录与权限,既麻烦又不安全。
9. **按模型特长分工**:作者用不同模型分别做主力开发、运维排障、浏览器/电脑操控。他还主张"做决策和管理的模型必须是最强的,不要用弱模型指挥强模型"。

## CI 中台(五步)

Agent 写完提交 PR 就结束,**不能自己上线**。之后由 CI 中台:审查 → 检查 → 合并 → 发布 → 核实(线上确认运行的版本包含这次改动)。

- 审查者与作者**不同模型**(Claude 写、Codex 审),审查者**只读、不能联网、读不到密钥**,只报真会出错的问题,不报风格。
- **最多审 3 轮**(作者说借鉴了 Anthropic 的代码审查文章;我读到的该文摘要([04](04-claude-code-review流水线.md))里没有出现"3 轮"这个数字,但那只是摘要,不能据此断言原文没有;以作者表述为准,出处待查)。
- 检查在每任务一台全新虚拟机里跑,跑完连机器带身份一起删。审查和检查是写死在 GitHub 上的合并规则。
- 作者自报:两周 4 个项目审了 298 个 PR,报 333 条问题,306 条合并前修掉,最严重一档 51 条;一次审查中位数约 2 分钟,占该任务 5%–15% token;从提交到上线中位数 2–3 分钟。

## "批奏折":什么必须问人

必须先问的只有几类:**删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限**,其余 agent 自行做完上线。早期曾一天推几十条卡片,严重干扰注意力。

- 仓库里有"卡兹克定的事"(记录作者亲口做过的决定,带原话和日期)和"定了不做的事"。**定过的事 agent 不再问第二遍。**
- 用户反馈**没有交给 agent**:作者每条亲自看,把有价值的再转给 agent,处理后亲自回信。

## 开源版 Agent-Autoloop(第二篇 + README)

- 内核约 **1600 行,零第三方依赖**,只做四件事:收事件、按规则分活、把活派给 agent、把每一步记下来。内核**不对外联网**、**不写死任何具体产品名**(有测试守护边界),同样输入得到同样结果(确定性)。
- 外围全是**插件**:事件、Agent、通道(飞书/钉钉/企微/Slack/Discord/桌面通知)、代码交付流水线。
- 约定:agent 只需在**最后一条回复**里交代结果;需要请示时附一段 `agent-autoloop` JSON 代码块(`ask`/`notice`/`resolve`/`later`/`events`)。JSON 写错时只让它在原会话里重写那一段,不重做业务。
- 四个内核机制:
  1. **挂起零消耗**:agent 发出卡片就退出,等待期间不占进程、不花 token,人回复后"读档"继续;同一问题不会再问。
  2. **事件溯源**:追加式账本,先落账再回"收到";断网后重发,同一件事只记一次;任一轮"为什么开始、用哪版规则、哪台机器接的、结果如何"可回溯。
  3. **指令数据分离**:外部人写的内容单独放文件、标为资料,不混入给 agent 的指令,用于防提示注入。
  4. **跳数熔断**:agent 每叫醒下一个 agent 层级加一,**超过 8 层自动停止并发卡片**,防止 A 叫 B、B 叫 A 的死循环烧额度。
- 场景模板:早报、跟进 GitHub Issue 等;"每 5 分钟从外面看一眼网站能否打开,能开就什么都不干、不花 token"这类**脚本先过滤、不叫醒模型**的做法。
- 作者自述:这是 1.0.0,可能有 bug;README 写明目前仅支持 macOS/Linux,Windows 待定。

## 与 DeepSeek 的差异

| 议题 | DeepSeek | 卡兹克 |
| --- | --- | --- |
| Agent Loop 在哪 | 云端无状态容器,端点装 daemon | 本地 Mac,事件靠长轮询拉取 |
| 为什么 | 常在线、不依赖单机 | 凭证和权限不想在云上复制,国内网络与浏览器任务不适合云 |
| 路由 | Router 会话(LLM)+ 订阅直通 | 确定性内核 + `rules.json`,**不用 LLM 路由** |
| 抑制噪声 | 代码过滤 + 语义判断 | 规则 `tell: needed` + 脚本先过滤 |
| 安全 | 作者承认是开放问题 | 只读审查者、全新虚拟机、指令数据分离、跳数熔断 |
