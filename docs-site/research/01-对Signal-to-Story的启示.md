# 对 Signal to Story 的启示(研究假设,待人工确认)

> 第二版,2026-11-05。这是**假设清单**,不是已采纳的决策。采纳前需与 [总体架构 SPEC](../spec/Signal-to-Story总体架构-SPEC.md) 的边界对齐,并写入相应 plan。
> 依据:[00-综合判断.md](00-综合判断.md) 与 [sources/](sources/)。

## 1. 先承认一个前提:我们已经有了一半

| 本项目现状 | 对应的研究概念 |
| --- | --- |
| 外部接入网关:文字/链接 → 原子保存信源 → 候选选题,回执、防重、撤销 | DeepSeek 的 Source/Trigger;卡兹克的统一事件格式与去重 |
| 状态机、幂等键、重试上限、成本字段(总体 SPEC §9) | Ticket/Assignment;卡兹克的追加式账本 |
| Agent 只出 Proposal/Draft,人批准与发布 | Mandate;卡兹克"agent 提交 PR 就结束,不能自己上线" |
| 不可变 revision、人工提审与审核 | 审批绑定具体 commit;0xwhrrari 的"权限在模型之外" |
| 云端 HTTPS 收录(Dot),**明确不使用个人 Mac** | 与卡兹克"本机长轮询"的立场相反,见 §4 |
| 路线图里的"IM / 分享 / 浏览器采集入口 → 待审核" | 两个来源的共同出发点:事件触发,人只做决策 |

所以真正需要补的,不是"事件中台"本身,而是它下游的几件小事。

## 2. 按"小、可移植、与现有边界不冲突"排序的借鉴点

| # | 借鉴点 | 来源 | 对应到本项目 | 代价 |
| --- | --- | --- | --- | --- |
| 1 | **"必须问人"的清单化** | 卡兹克 | 把发布、对外发消息、花钱(视频生成)、改账号权限、删数据列成显式的批准类别,其余 Agent 自行推进到"待审核"。目前人工门禁散落在各页面里 | 小,主要是规则表 |
| 2 | **决定记忆**:记录人亲口做过的决定与拒绝过的做法,带原话和日期,Agent 不再重复问 | 卡兹克 | 对应选题评审、风格偏好、"定了不做的选题"。可先做成一张表或一份受控文档 | 小 |
| 3 | **循环上限**:草稿↔评估最多 N 轮;Agent 触发 Agent 的跳数上限 | 卡兹克、0xwhrrari | 当前 SPEC 只写了"最大尝试次数",没覆盖"草稿评估往返"和"链式触发" | 小 |
| 4 | **指令数据分离**:外部来源(链接、转发内容)标记为资料,不进入指令位置 | 卡兹克;DeepSeek §8.4 | 我们的外部接入会收来自 IM 和网页的文字,**这是真实的提示注入入口**。目前 SPEC 没有专门条款 | 中,涉及 Context Pack 的构造 |
| 5 | **生成者与评估者分离 + 评估者只读** | Anthropic、卡兹克 | 草案生成后,由另一个只读的 Agent 按清单检查(来源、事实、风格、合规),输出给人审 | 中,需要先写清单 |
| 6 | **脚本先过滤,没事不叫醒模型** | DeepSeek Fast Path、Autoloop | 接入网关的去重、来源白名单、分类可以先用确定性规则,只把需要语义判断的送给模型 | 小 |
| 7 | **挂起零消耗**:等人审期间不占进程、不烧 token | Autoloop | 我们本来就是"Proposal 入库,人在 Console 里审",天然符合;应在 SPEC 里写明为原则 | 几乎为零 |
| 8 | **以"待人处理"为中心的任务中心** | DeepSeek 面板与 Ticket 阶段 | 任务中心先显示"等我回答 / 等我审 / 失败阻塞",健康状态不占位 | 小,纯前端 |
| 9 | **行为级 eval** | Google | 针对离散行为(信息不足时是否提问、是否标注来源、是否越权)建立小而快的检查 | 中 |
| 10 | **规则写两遍**:指引 + 机械检查 | 0xwhrrari | 项目已经在做(CLAUDE.md + lint/测试),可延伸到内容规则 | 小 |

## 3. 暂不建议借鉴

| 做法 | 为什么先不要 |
| --- | --- |
| Router/Worker 两级会话、订阅直通、Chain of Recall | DeepSeek 自己的结论是"当前团队规模下单个 Router 够用";我们是单人使用,并且 SPEC 要求出现真实长任务前不建 Worker |
| Agent Loop 在云端、端点装 daemon(BYOM) | 需要云与端点互信,作者自己把安全列为开放问题 |
| Watchdog(用模型判断 Worker 是否偏离目标) | 没有常驻 Worker 就没有对象 |
| 多模型分工(不同 agent 管开发/运维/浏览器) | 是卡兹克基于个人订阅与场景的选择,不是普适结论 |
| 自动合并/自动发布 | SPEC 当前阶段明确不做;只借"批准类别"的规则表达 |
| 完整的"中台 + 插件内核"(Autoloop) | 解决的是"本机命令行 agent 如何被事件唤醒";我们的 Agent 调用走 Edge Function/Supabase,不是命令行 |

## 4. 一个需要你做的真实取舍:本机 vs 云端

两个来源在这里立场相反,而且各有理由:

- DeepSeek:云端常在线,环境留在原处。代价是云与端点必须互信,提示注入一旦得手后果很大。
- 卡兹克:全部在自己的 Mac 上,凭证不出本机。代价是机器必须常开,国内外访问和浏览器类任务有各自的坑,不适合多人。

**我们的 README 已经决定"Dot 云端直接调用 HTTPS 收录 API,不使用个人 Mac"。**这一决定在"只做收录"的范围内成立。但如果将来要做**自动创作**(下一阶段),需要访问登录态浏览器、本地素材或本机 CLI Agent 时,会碰到卡兹克描述的同一问题。建议到那时再单独决定,不在这一轮预设。

## 5. 与现有边界的冲突清单

| 研究做法 | 项目约束 | 结论 |
| --- | --- | --- |
| 执行环境默认无审批运行命令 | Agent 不得直接执行任意 SQL;不持有高权限密钥 | 不借鉴 |
| 事件常驻监听/长轮询 | 当前是推送式收录 | 保持推送式 |
| 把外部人写的内容交给 agent 读取 | 总体 SPEC 要求"最小必要上下文" | 需要补 §2-4 |
| 评估者/审查者多模型 | 预算与成本字段需要先就位 | 先单评估者 |

## 6. 待决问题

1. **你要的"自循环"是哪一环?**(a)采集→选题,(b)草稿的生成-评估-修改,(c)发布后数据回灌选题。根据上面的材料:(a)我们已有;(b)材料最丰富,且有 §2 的 5、3、4;(c)所有来源都是**弱项**——卡兹克系统记录了数据但没说如何反哺,知识猫的批评也在此,我没读到原文。如果你最关心(c),目前的研究依据最薄弱。
2. **"内容合格"的清单由谁定义?**这是从代码迁移到内容时唯一没有现成答案的部分。
3. **是否先做 §2 的 1–4、6–8(都不涉及新增 Worker 或新架构)?**我的判断是这些小改动价值/成本比最高,并且不预设本机/云端的选择。
4. 引入"仅记录模式"(主动行为先只写下"本会做什么")是否接受?这个做法来自 DeepSeek 哲学文档,我没有在卡兹克材料里看到对应物。
