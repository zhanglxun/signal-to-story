核心问题解答：自造 Agent CLI 还是做「中间层 + 双模驱动」？

推荐架构

结论：不要从零重复造底层通用 CLI（如重写一套 Pi 或 OpenCode），而是构建「星火 Content Harness 中间层 + 可插拔双模驱动（Cloud API + Headless CLI Bridge）」。

1. 为什么不从头造通用 Agent CLI？
Pi (pi-mono)、OpenCode、Codex CLI、agy CLI 已经把底层流式解析、文件沙箱、MCP 挂载和终端交互做到了极致。自己重造底层 CLI 不会产生内容业务壁垒，反而陷入无休止的 SDK 维护。
2. 我们的真正核心壁垒在哪？（自研 Content Harness 中间层）
通用 CLI 不懂你的「内容选题评级、指令与不可信网页分离、租户过往审美记忆（Decision Memory）、草稿与只读审查员 3 轮自循环、分镜毫秒级配音对齐、以及跨平台人工审核门禁」。把这一层做成标准的 TypeScript 服务（Sense Agent Harness），才是可对外售卖的 SaaS 核心资产！

目标设计的「三步物化协议」：
① Checkout：把数据库 Brief、记忆与爬虫原文写成 /workspaces/job_id/*.md；
② Execute & Session：以 stdin 传入指令调 CLI，记录 cli_session_id 支持多轮 --resume；
③ Commit：将 outputs/draft.md 写回数据库提案表并上传附件。

  • 单机/容器合体部署 (npm run start)：1 个 Node 进程同时托管 dist/ 网页 + 跑后台 Loop + 内存级注入租户 API Key

四阶段平滑演进路线图（不推翻现有 MVP，逐步插拔升级）

Phase 1 · Agent Harness 内核与多模型中间层就位（方向 A 基座） 最高优先级

1) 建立统一模型与 CLI 适配层（打通 Qwen / Kimi / DeepSeek 及 Pi / OpenCode CLI 调用，解决线上 AI 出稿阻塞）；
2) 落地「指令数据隔离 Context Pack」、「决定记忆表 (decision_memories)」与「生成 ↔ 只读评估（≤3轮）」自循环；
3) 升级任务中心为“待我拍板 / 待我审核 / 异常阻塞”视图。

Phase 2 · Web 视频工坊（Video Studio）全链路实装（方向 C） 核心差异化能力

1) 将 video-factory 封装为服务端异步 Worker，分镜数据入库 Postgres，产物自动存 OSS；
2) 在 sense-console 实装分镜画布：一键大纲拆解分镜、在线改词 TTS 试听、万相 2.7 单镜重抽、多轨合成在线播放；
3) 视频成片接入统一多平台发布排期（视频号、抖音、小红书、YouTube、X）。

Phase 3 · 多入口个人内容助手贯通（方向 B：飞书 / 企微 / 网页速记） 高频日常入口

1) 接入首个主力双向 IM（飞书或企微机器人）+ 控制台顶栏极简速记框；
2) 实现「随手发链接/想法 → 自动检索核查 → Harness 自循环出稿 → 推送 IM 审核卡片 → 点击授权自动发布」。

Phase 4 · 独立读者站 sense-site 与 SaaS 多租户商业化（方向 D + SaaS） 对外展示与变现

1) 按 P1–P4 建设 sense-site，支持已审核图文/视频一键发布为公开/注册读者快照；
2) 完善租户自助开户、模型 BYOK 密钥配置、配额账单与 Docker Compose 一键独立部署包。
